The path a request takes

One prompt, seven hops

The single most important structural fact: a modern inference server is not one program. Prefill and decode are split across different machines with different hardware profiles, because they are different workloads that happen to share a model.

01edge

Terminate, authenticate, pin a region

Auth, org quota, abuse checks, and — increasingly the interesting part — data-residency routing. Anthropic expanded inference into Asia and Europe rather than serving everything from US capacity: a legal constraint expressed as network topology. Worth noticing as a general pattern, because it is one of the few places where regulation directly shapes where silicon is installed.

02admit

Admission control — the layer everyone forgets

A queue with no admission policy converts overload into universal timeout. Production servers shed, prioritise and rate-limit here, and route by expected cost: short or cache-hot prompts stay local, long uncached prefills get sent to dedicated capacity. Published results show 54% higher throughput and 64% lower P90 TTFT from selective routing alone.

This is also where your tier lives. Batch API traffic is admitted at a different priority to interactive traffic — same model, same silicon, different queue.

03cache

Check the prefix cache before computing anything

The cheapest prefill is the one you skip. Claude's API exposes this mechanism directly: mark a breakpoint, and the system hashes the prompt prefix up to that point and looks for stored KV. A hit costs 0.1× the price of fresh input tokens — a 10× discount that is really a latency discount wearing a price tag.

04prefill

Prefill: one enormous parallel pass

Every token of the prompt is processed at once, producing the KV cache for the sequence. Big dense matmuls, high arithmetic intensity, GPU/Trainium fully saturated. Cost scales with prompt length — which is why a 100k-token context costs real money in latency, not just billing.

05handoff

Move the KV cache to a decode worker

The hard engineering problem in disaggregated serving. Multi-gigabyte KV tensors move over NVLink/NeuronLink, CXL or NVMe-oF, and if the transfer is slower than the prefill it saved, the whole design is a loss. This hop is why disaggregation stayed a research idea until interconnects got fast enough.

06decode

Decode: N sequential passes, one token each

Each token reloads the full model weights and re-reads a KV cache that grows with every step. Arithmetic intensity collapses to roughly 0.5 ops/byte, and accelerators spend over 70% of decode time waiting on memory. No amount of FLOPs fixes this — it is a bandwidth problem, and it is why decode gets its own hardware profile.

07stream

Stream, because perceived latency is the product

A 12-second answer that starts in 300 ms feels faster than a 4-second answer delivered as a block. Streaming is not a UX nicety bolted on at the end; it is the reason the entire stack optimises time-to-first-token as a separate metric from throughput.

The physics underneath

Why one model needs two kinds of machine

This is the single idea that explains most of the architecture above. It is also the idea that explains why your local RAG feels slow in a way that no amount of code tidying will fix.

Decode speed is not a software problem. Tokens per second is memory bandwidth divided by model bytes — and on your Mac, that is a number you can look up rather than optimise.

The economics

Continuous batching is why a token costs cents

Serving efficiency comes from keeping the accelerator busy. The technique that made LLM serving commercially viable is unglamorous: never idle a batch slot waiting for the slowest sequence to finish.

Worked example

Now run a RAG on it

RAG is the clearest way to see the stack, because it doesn't make one kind of request — it makes three, and only two of them are inference at all. Once you can name which is which, most RAG performance advice sorts itself into "true" and "cargo cult."

Three shapes, and why it matters

Sorting RAG's calls by shape rather than by name is what turns the architecture from a diagram into a set of decisions:

Step Shape Scales with Right lever
Embed chunks Prefill only, huge batch Total tokens in the corpus Batch size, device, model size
Embed query Prefill only, batch of 1 Nothing — it's ~20 tokens Keep the model resident. Nothing else.
Search + rank Not inference Corpus size, and weakly Index choice — but only past ~100k vectors
Generate Big prefill → short decode Chunks retrieved × chunk size Prefix caching, fewer/smaller chunks

RAG inverts the usual workload. Ordinary chat is a short prompt and a long answer — decode-dominated. RAG is a long prompt and a short answer — prefill-dominated. Retrieving 5 chunks of 400 tokens means every question carries ~2,000 tokens of context to produce maybe 300 tokens of output. So a RAG service stresses the half of the engine that a chatbot barely touches, and the levers that help are different ones.

The cache boundary — the most expensive detail in RAG

Prefix caching works by hashing everything up to a breakpoint. That single mechanic decides your entire cost structure, and it is easy to get exactly backwards.

Nothing in RAG fails loudly. A broken cache boundary, a chunk size that splits every table in half, a reranker that never fires — all of them return plausible answers. Only measurement tells you.

The bridge to your machine

Which of these you can actually have

Map every datacenter technique onto a single M3 Pro and a clear picture emerges: you can reproduce almost all of the engineering, and none of the parallelism. That boundary tells you exactly where to stop optimising.

Technique What it does at scale On an M3 Pro / 18 GB Worth your time?
Resident model Weights never leave accelerator memory; a cold load is an incident, not a normal path Same idea exactly — OLLAMA_KEEP_ALIVE=-1 and a long-lived process ▲ biggest single win
Prefix / prompt cache Hash the prompt prefix, reuse stored KV, skip prefill; 10× cheaper on the Claude API llama.cpp caches the KV for a stable prefix — put your system prompt first, context after ▲ free, do it
Batched embedding Hundreds of chunks per forward pass on a warm GPU fleet Batch 128 on MPS instead of 32 on CPU — the same lever, three orders of magnitude smaller ▲ 10–30× on ingest
Continuous batching Keeps every slot full; the core unit-economics technique Meaningless at concurrency 1 — you are the only request ✕ skip entirely
Prefill/decode split Separate hardware pools tuned to opposite bottlenecks One chip, one memory bus. The split has nowhere to go ✕ not available
Speculative decoding A small draft model proposes tokens, the large one verifies in parallel Genuinely available locally, and the one real lever on decode speed ▲ try after baseline
Tensor / pipeline parallel One model sharded across many chips over a fast interconnect Nothing to shard across ✕ not available
Admission control Sheds and prioritises load so overload degrades gracefully Only matters once something other than you calls the service ✕ later, if ever

The split worth remembering. Four of the eight techniques above are unavailable at concurrency 1, and they are precisely the ones that make cloud inference cheap — batching, disaggregation, sharding, admission control all exist to amortise hardware across many simultaneous users. The ones that make it fast — residency, prefix caching, batched embedding, streaming — need no other users at all, and are entirely available to you.

So the sensible target for a local stack is not parity. It is: land within roughly 2× on perceived latency, accept that per-token cost will be much worse, and be clear-eyed that what you bought is control over where the data sits — not speed and not economy.

What to take away

Four ideas do most of the explanatory work, and they generalise well beyond RAG:

  1. Ask what a step is bound by — compute, memory bandwidth, or neither — before optimising it. Half of all performance work is spent on steps that were never the constraint.
  2. Cold starts masquerade as slowness. Loading a model, importing a framework, evicting a cache: these dominate naive systems and disappear entirely under a resident process. Fix residency before you fix algorithms.
  3. Batching is an amortisation trick, and it needs something to amortise over. With one user it buys nothing on the query path — but on ingest, where you have thousands of chunks, it is the whole game.
  4. Perceived latency is a separate metric from throughput, and the two are often improved by opposite decisions. Decide which one you are optimising before you touch anything.
